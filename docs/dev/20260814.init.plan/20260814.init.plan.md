# Koishi PicStatus 移植规划

## 目标与原则

- 使用纯 TypeScript、`systeminformation` 与 Koishi Puppeteer 重建 `nonebot-plugin-picstatus`，尽量还原默认状态图的布局、组件、背景效果与信息密度喵。
- 支持 Windows、Linux、macOS、Docker，以及 QQ、Telegram、Discord、Kook 等不同 Koishi 适配器喵。
- 核心逻辑仅依赖 Koishi 公共 API，OneBot 等平台能力作为可选增强，单项采集失败不得导致整张图片失败喵。
- 上游为 MIT License，发布时保留其版权与许可文本，并在 README 中注明移植来源喵。

## 第一阶段：默认状态图与核心采集

- 将 `puppeteer` 和 `http` 声明为必需服务，使用 `systeminformation` 进行纯 Node.js 跨平台采集喵。
- 建立统一的 `StatusSnapshot` 数据模型，并用 `MetricResult<T>` 表达 `ok`、`unavailable`、`unsupported` 与 `error` 喵。
- 采集 CPU 型号、物理与逻辑核心、频率、占用率、内存、Swap、磁盘容量、磁盘 IO、网络 IO、系统信息与运行时间喵。
- 采集 Koishi 运行时间、当前时间、进程 CPU/内存排行，以及网站状态码、响应耗时和失败原因喵。
- 建立周期采集缓存，为 CPU、磁盘 IO、网络 IO 和进程状态提供稳定采样，首次无差值时显示未知喵。
- 迁移上游默认 HTML/CSS 视觉，提供默认、深色、无模糊、无圆角和无阴影主题效果喵。
- 支持组件排序与开关、JPEG/PNG、截图质量、渲染宽度、采集超时、忽略正则和调试日志喵。
- Puppeteer 渲染时内联 HTML、CSS、字体和背景，等待字体、图片与布局稳定后截取根容器，并始终关闭页面喵。
- Docker 环境明确显示“容器资源”，避免将容器指标误认为宿主机指标喵。

第一阶段验收标准为 Windows、Linux、macOS 均能生成结构接近上游默认模板的完整状态图，任一采集器失败仍可出图喵。

## 第二阶段：Bot、消息统计与背景

- 通过 `ctx.bots` 采集 Bot 平台、账号、昵称、连接时长和在线状态，支持显示当前 Bot 或全部 Bot 喵。
- Bot 头像缺失或下载失败时使用内置默认头像，平台专有资料接口只作为增强来源喵。
- 使用 Koishi 中间件统计接收消息，并通过发送生命周期统计发送消息，不在核心中维护适配器 API 名称表喵。
- 消息计数提供 `memory | database` 配置，默认 `memory`，并按 `platform:selfId` 隔离喵。
- `database` 模式使用可选 database 服务跨重启保存；服务不可用时警告并回退到内存喵。
- 支持配置 Bot 断开时是否重置内存计数，并区分连接时长与持久化累计消息数喵。
- 支持当前消息或引用消息中的第一张图片作为临时背景，并使用 Koishi 通用消息元素解析喵。
- 实现内置、本地文件、本地目录、固定 URL 和无背景 Provider，按“用户图片、配置来源、内置背景”降级喵。
- 本地目录随机选择受支持图片；URL 下载校验状态码、MIME、大小与超时喵。
- 核心稳定后加入有界背景预加载队列、失败重试、超时与插件卸载清理喵。
- 配置采用 Koishi Schema 分组与驼峰命名，不机械保留上游 `PS_*` 名称喵。
- 默认指令为 `picstatus`，保留“运行状态、状态、zt、yxzt”等别名，并在别名冲突时跳过冲突项喵。

第二阶段验收标准为任意 Koishi 适配器均可执行指令并收到图片，平台增强失败不会影响通用结果喵。

│  │  └─ preloader.ts          # 第二阶段的有界预加载队列

- `index.ts` 只负责装配，不直接采集、拼 HTML 或处理平台专有事件喵。
- `collectors` 只产生结构化数据，不读取 Session、不生成展示文本，也不接触 Puppeteer 喵。
- `view.ts` 负责所有显示文本、缺失值和组件可见性，保证模板保持简单且可测试喵。
- `runtime` 保存随时间变化的状态；插件卸载时统一停止定时器、等待任务并释放监听器喵。
- `command.ts` 仅使用 Koishi 通用消息元素和 `h.image()`，不实现 QQ 按钮、QQ Markdown 或 OneBot 专用发送分支喵。
- `assets` 必须加入 npm `files`，许可证文件同时随包发布；默认模板代码进入 `lib`，避免运行时读取 `src` 喵。
- 第一阶段先创建除 `bot.ts`、`counter.ts` 和 `preloader.ts` 以外的结构，第二阶段再补齐这些模块喵。

## 第三阶段：双层扩展体系

- 面向普通用户提供相对于 `ctx.baseDir` 的资源目录，默认解析为 `data/picstatus` 喵。
- 路径配置使用目录段数组，拒绝绝对路径、`..` 和解析后逃逸资源根目录的路径喵。
- 普通用户扩展仅允许主题覆盖，可提供 `theme.json`、CSS、背景图片和静态字体喵。
- 主题不得替换完整 HTML，也不得从目录执行 `.js`、`.mjs`、`.cjs` 或 TypeScript 代码喵。
- 主题目录使用防抖文件监听刷新索引；新文件无效时保留上一个有效主题并记录错误喵。
- 面向开发者公开类型化 `PicStatus` Koishi Service，由独立 Koishi 插件注册 Collector、Background Provider 与 Template Renderer 喵。
- Collector 支持 `normal`、`once`、`periodic` 与基于两次采样计算速率的模式，并声明唯一名称和超时喵。
- Background Provider 接收数量与取消信号，返回图片 Buffer、MIME 和来源，并可声明是否允许预加载喵。
- Template Renderer 声明所需 Collector，接收统一快照与背景，可返回图片 Buffer 或调用公共 Puppeteer 渲染工具喵。
- 重复注册默认拒绝并记录来源插件，扩展卸载时自动注销注册项、定时任务和缓存喵。
- JSON 仅用于主题元数据和静态配置，动态采集与渲染逻辑必须由标准 Koishi 插件提供喵。

第三阶段验收标准为示例扩展插件可以分别新增采集器、背景 Provider 和图片模板，禁用后能完整清理喵。

## 公开接口

- `StatusSnapshot` 统一承载系统、CPU、内存、磁盘、网络、进程、网站、Bot 和页脚数据喵。
- `MetricResult<T>` 隔离平台差异，模板不得依赖 `systeminformation` 或适配器的原始对象喵。
- `CollectorDefinition`、`BackgroundProviderDefinition` 与 `TemplateDefinition` 构成开发者注册 API，并支持生命周期清理喵。
- `counterStorage` 默认为 `memory`，可选择 `database` 喵。
- `resourcePath` 默认指向 `ctx.baseDir/data/picstatus`，所有用户资源访问都限制在该根目录内喵。

## 测试与验收

- 单元测试覆盖单位换算、持续时间、排序、正则过滤、路径限制、差值速率与失败降级喵。
- 模拟 Windows、Linux、macOS、Docker、无 Swap、无磁盘 IO 和空进程列表数据喵。
- 测试内存与数据库计数、数据库缺失回退、Bot 断开重置和多 Bot 数据隔离喵。
- 测试用户背景、本地目录、URL、错误 MIME、超大响应、超时和内置背景回退喵。
- 使用 Puppeteer 截图验证图片非空、尺寸稳定、中文字体正常、长文本不溢出且组件不重叠喵。
- 至少在 Windows 本机、Linux CI 和 Docker 中执行构建与渲染冒烟测试喵。
- 对照上游示例图人工检查信息层级、圆环、卡片布局、背景遮罩、模糊效果与页脚，不要求逐像素一致喵。

## 已确定的默认选择

- 首版使用纯 TypeScript，不引入 Python 后端喵。
- Puppeteer 是必需服务，缺少时由 Koishi 阻止插件加载喵。
- 追求上游行为与视觉相近，但配置采用 Koishi 原生设计喵。
- 普通用户只通过 JSON、CSS、字体和图片修改主题，不允许执行目录脚本喵。
- 开发者通过独立 Koishi 插件和公开 Service API 扩展动态能力喵。
- 消息计数默认使用内存，可选 database 持久化喵。
- 第一阶段完成默认状态图，第二阶段补齐 Bot 与背景，第三阶段开放稳定扩展 API 喵。
